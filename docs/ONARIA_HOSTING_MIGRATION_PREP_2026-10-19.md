# ONARIA Cafe24 → 가비아 호스팅 이전 준비

작성일: 2026-10-19 (KST)
Cafe24 호스팅 만료일: **2026-12-03**
상태: PREP / 읽기 전용 사전 조사
담당: ARI 총괄, JINI 현황 조사·독립 검증

현재 운영 인프라가 이미 가비아로 이전되었을 가능성이 있으므로, Cafe24의 잔존 의존성부터 확인하고 불필요한 이전은 하지 않는다.

## 확인된 공개 현황 (2026-10-19)
- onaria.ai.kr과 api.onaria.ai.kr의 A 레코드: 1.201.113.102, 조회 TTL 600초
- onaria.ai.kr 네임서버: ns.gabia.co.kr, ns1.gabia.co.kr, ns.gabia.net
- 두 호스트의 /health HTTPS 200, 응답 Server: nginx/1.24.0 (Ubuntu)
- 공개 TLS 인증서 표시 만료일: 2026-12-20 01:07:09 UTC
- 루트 도메인의 MX/TXT 조회 결과 없음. 개별 하위 도메인 또는 외부 발송 의존성은 미조사.
- 기존 2026-09-12 문서의 Cafe24 Apache→Node 8787 구성은 과거 기록. 현재 운영이라고 단정하지 않는다.

## 현재 방침
운영 서비스 중단, DNS 변경, 계약 해지, 실제 데이터 이전, DB·비밀정보 변경은 실행하지 않는다. 먼저 인벤토리와 검증 계획을 작성한다.

## 1. 기존 Cafe24 환경·웹·DB·의존성 체크리스트
- [ ] Cafe24 상품명, 만료 2026-12-03, 계약/자동연장/요금, 권한과 서버 주소 확인.
- [ ] 실제 요청을 받는 서버가 Cafe24인지 가비아인지 운영 로그·DNS·배포 이력으로 대사.
- [ ] 웹 루트, 홈/관리자/지원/계정삭제/PWA, API, nginx 또는 Apache, Node 런타임, systemd, cron과 웹훅 목록.
- [ ] 회원 및 AI비용 SQLite DB의 실제 경로, 데이터 용량, WAL 여부, 쓰기 프로세스, 외부 파일/첨부·RAG 인덱스 위치.
- [ ] Naver/Google/Kakao/Apple 인증 리다이렉트, API 주소, 앱 링크, 서버 발신 IP 의존성, 외부 AI/SMS/푸시 연계.
- [ ] MX·SPF·DKIM·DMARC 및 SMTP/알림 메일, 외부 고객 문의 주소가 Cafe24 메일에 의존하는지 확인.
- [ ] 기존 웹·API·인증서·백업·도메인·메일 중 Cafe24 해지 후 사라질 항목만 별도 표시.

## 2. 가비아 대상 호스팅 사양 확정 체크리스트
- [ ] 서버 계약 상품/ID, Ubuntu 버전, vCPU·RAM·디스크·여유 공간, 월간 트래픽, 과금과 백업 옵션 확인.
- [ ] 현재 운영이 이미 가비아라면 이중 이전하지 않고, 기존 ari-prod-01 및 ONARIA 경로의 실체를 먼저 확인.
- [ ] Node 버전, nginx 설정, systemd, 내부 8787과 공개 80/443, TLS 갱신 주체·상태 확인.
- [ ] ONARIA만의 경로, 서비스, 환경변수, DB, 백업과 모니터링을 타 프로젝트와 완전히 분리.
- [ ] 실제 피크 CPU/메모리, 파일/DB 성장률, 동시 접속을 측정하여 리소스 여유·복구 목표 정량화.
- [ ] API 원본 HTTPS 주소는 api.onaria.ai.kr로 유지할 수 있는지, 관리자 쿠키와 리다이렉트 영향 확인.

## 3. 전체 백업과 무결성 체크리스트 — 승인 후 실행
- [ ] Cafe24와 가비아의 운영 웹 파일, 소스/배포 커밋, 업로드, DB, 설정, 작업 스케줄, 인증서 갱신 구성의 백업 범위 작성.
- [ ] 각 SQLite DB는 일관성을 위해 SQLite Online Backup API 또는 sqlite3 .backup 활용. 실행 중 DB 본체 파일만 복사하는 방식 금지.
- [ ] 데이터·웹 설정·비밀파일은 접근 제한된 암호화 저장소에 보관. 개인키·토큰·고객 원문을 채팅/공유폴더/Git에 올리지 않음.
- [ ] 백업 시각·원본 경로·DB 크기·건수·SHA-256·integrity_check 결과 기록. 오프사이트 복사와 보관 정책 확인.
- [ ] 실제 전환 직전의 최신 쓰기까지 복원하려면 증분·최종 스냅샷 및 쓰기 동결/복제 방안을 사전 결정.

## 4. 사전 복원 테스트 체크리스트
- [ ] 접근 통제된 스테이징에서 복원. 운영 회원 원문과 비밀정보 외부 노출 금지.
- [ ] 백업 DB의 건수, 스키마, 인덱스, 설정, 암호화 파일 연계 및 복구 시간 검증.
- [ ] 웹 홈, 관리자 인증, /support, /health, API, 앱 로그인 4종, 계정삭제 흐름 확인.
- [ ] 테스트 중 실제 메일·SMS·유료 AI 호출·실사용자 푸시 발송 방지.
- [ ] SSL 인증서 SAN·자동 갱신, HTTPS, 소셜 콜백, 앱 링크, PWA 캐시 확인.
- [ ] 장애 가정 복원 시간, RTO/RPO, PASS/FAIL/NOT RUN과 롤백 조건 기록.

## 5. DNS TTL 및 전환 체크리스트
- [ ] 가비아 DNS 관리툴에서 A, AAAA, CNAME, NS, MX, TXT, CAA와 TTL 전부 기록.
- [ ] 현재 A TTL은 600초. 실제 IP 전환 필요 시 48~72시간 전 300초 변경 계획을 승인받아 수립.
- [ ] NS 변경을 피하고 기존 가비아 네임서버 유지 우선.
- [ ] 전환 전에 신규 서버를 호스트명·SNI로 검증하고 앱/웹/API 동작을 대조.
- [ ] SQLite를 두 운영 서버가 동시에 쓰면 데이터 정합성이 깨질 수 있으므로 쓰기 중단 또는 검증된 복제 전략 확정.
- [ ] 컷오버 담당자, 모니터링, 장애 롤백 기준, 기존 서버 유지기간 최소 72시간 확인.
- [ ] IP만 되돌려서는 새 DB 기록이 복원되지 않으므로 데이터 역동기화 계획 별도 수립.
- [ ] 24시간 및 72시간 관찰 후 Cafe24 잔존 의존성 없음 확인.
