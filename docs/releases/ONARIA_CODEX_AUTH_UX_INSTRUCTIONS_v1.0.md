# ONARIA 회원·인증·기록 UI/UX 개선 작업지시서

문서 버전: 1.0 · 작성일: 2026-10-11 KST · 대상: ONARIA 전용 Codex

## 1. 역할과 목표

너는 ONARIA의 Flutter·Node.js 개발, UI/UX 설계, 보안 검토와 QA를 담당한다. 이 문서를 읽고 실제 저장소의 최신 상태를 확인한 뒤, 안전한 로컬 개발·검증을 순서대로 진행한다. 분석이나 계획 제시만으로 멈추지 않는다.

목표는 ‘쉽게 시작하고, 한 회원의 기록을 안전하게 이어가며, 복구와 탈퇴까지 확실하게 처리하는 경험’이다. 화면을 예쁘게 바꾸는 것으로 완료하지 말고 화면·인증·세션·회원·기록·삭제의 실제 동작을 일치시킨다.

이 문서가 과거 성공 보고보다 우선하는 검증 기준이다. 실제 소스와 실행 결과가 다르면 차이를 기록하고 현재 증거에 따라 판단한다.

## 2. 시작 전 필수 확인

- 프로젝트 경로: `/Users/ari/ARI/projects/onaria`. 다른 환경이면 ONARIA 저장소를 먼저 확인하고 경로를 조정한다. 다른 프로젝트를 추측해서 열거나 수정하지 않는다.
- 루트와 작업 경로의 `AGENTS.md`, `docs/ARI_COMPLIANCE_STANDARD.md`, pubspec/package 파일을 읽는다.
- 브랜치·HEAD·remote·전체 git status를 확인한다. remote 인증정보는 출력하지 않는다.
- 2026-10-11 확인값은 `codex/apple-android-20261006`, HEAD `1aef3815c8e25022a948c4307e1c755e5cc8507b`이며 많은 기존 미커밋 변경이 있었다. 이 값은 현재값이라고 가정하지 않는다.
- 기존 수정·미추적 파일·사용자 데이터·서명 설정을 보존한다. 강제 reset/checkout/stash, 덮어쓰기, 자동 일괄 커밋을 하지 않는다.
- 별도 작업 트리가 필요하면 기존 미커밋 후보를 빠뜨리지 않도록 적용 범위와 파일 해시를 기록한다. HEAD만 복제한 작업 트리를 현재 앱과 동일하다고 간주하지 않는다.
- origin/main 비교와 CI 조회는 읽기 중심으로 수행한다. 기존 로컬 인증 후보와 main 개선사항을 리뷰 없이 병합하지 않는다.
- 다른 실행 중 작업이 같은 파일을 수정하고 있다면 충돌을 피한다. 작업 시작/종료의 변경 목록을 비교한다.

먼저 읽을 문서:

1. `docs/releases/ONARIA_AUTH_LIFECYCLE_AUDIT_2026-10-11.md`
2. `docs/releases/ONARIA_SIGNUP_BENCHMARK_DIRECTION_2026-10-11.md`
3. 최신 로컬 릴리스 리뷰·Build20 명세·기존 인증 테스트
4. `third_party/naver_login_flutter/ONARIA_PATCH.md`

## 3. 현재 알려진 사실과 미확정 사항

- A33의 `SDK: logged_out` 실패는 확인됐으나 실제 실패 원인은 아직 미확정이다.
- 플러그인의 취소/토큰 누락 반환 혼합, Dart logout 결과 무시, 중복 프로필 조회를 개선한 로컬 후보가 존재한다. 중복 구현하거나 pub cache를 직접 수정하지 않는다.
- A33 확인 당시 Android16·ONARIA 1.0.0+20, 네이버 앱 패키지 없음·Chrome 있음이었다. 재시험 시 다시 확인한다.
- 마음기록은 기기 공용 키에 저장되고, 기존 탈퇴 흐름은 기기 기록·초안을 보존한다. 계정별 소유권과 삭제 안내의 정합성을 우선 조사한다.
- 기존 검증값: 백엔드489 PASS, 최종 인증 Flutter33 PASS, Android 인증 모듈 컴파일 PASS. Flutter 전체177 PASS/1 SKIP는 마지막 Dart 결과파싱 수정 전 결과다. 새로운 변경의 PASS로 재사용하지 않는다.
- 후보 APK/AAB 설치, A33 실제 로그인, iPhone/Web 전체 회원 흐름과 운영 배포는 이 기록만으로 PASS가 아니다.

## 4. 디자인 원칙

- 밝고 따뜻한 ONARIA 톤과 기독교 중심 콘텐츠를 유지한다.
- Apple의 여백·명확한 위계, Toss의 한 화면 한 주요 행동, Airbnb의 탐색성, Notion의 간결한 구조, 당근의 친근한 한국어를 참고한다. 서비스 화면을 복제하지 않는다.
- 제공자 버튼은 각 제공자의 최신 브랜드 가이드와 접근성 요건에 맞춘다. 가입 제공자는 기존 네이버·카카오·Google·Apple을 보존한다.
- 한 화면에 주요 완료 버튼은 하나를 중심에 두고, 보조 행동을 명확히 구분한다.
- 오류를 짧은 한국어로 설명하고 다음 행동을 제공한다. SDK 코드·HTTP 상태는 진단 영역에만 두고 일반 사용자 화면의 주 메시지로 사용하지 않는다.
- 로딩, 빈 상태, 오프라인, 실패, 재시도, 처리 결과 미확인, 완료를 각각 설계한다.
- 화면 전환·재시도·뒤로가기가 입력과 동의를 무작정 지우거나 다른 인증 시도의 상태를 재사용하지 않도록 한다.
- 화면 내용이나 버튼이 시스템 내비게이션, 키보드, safe area에 가리지 않도록 한다.
- 터치 영역은 플랫폼 권고에 맞추고 최소 48 logical px를 기본 검토값으로 한다. 글자 확대 200%, 스크린리더, 명암 대비, 포커스 순서를 확인한다.
- Android 작은 화면, iPhone, iPad, 좁은/넓은 Web에서 동일한 의미와 안전한 동작을 유지한다. 화면 배치는 기기 특성에 맞춰 조정한다.

## 5. 화면과 사용자 여정

| 화면/상태 | 주요 내용·행동 | 필수 복구 동작 |
|---|---|---|
| 시작 | ‘로그인 또는 시작하기’, 서비스의 짧은 설명, 소셜 버튼 | 이전 성공 로그인 방식 표시. 방식이 현재 사용 불가하면 다른 연결 방법 안내 |
| 소셜 인증 중 | 외부 인증 진행 안내, 중복 탭 방지 | 취소·시간초과 구분, 늦게 도착한 이전 결과 차단 |
| 기존 회원 확인 | 인증된 ID로 서버 조회 | 기존 회원이면 추가 가입 폼 없이 진입. 장애/401을 미가입으로 처리하지 않음 |
| 미연결 계정 | ‘이 로그인 방식은 아직 연결되어 있지 않아요’ | ‘새로 시작하기’와 ‘기존 계정에 연결하기’. 사용자에게 중복 가입 위험 설명 |
| 신규 동의 | 필요한 약관·처리 안내·현재 연령 정책 | 필수/선택 구분, 선택 동의 미선택 기본, 내용 보기 후 진행 복귀 |
| 가입 완료 | 실제 서버 생성과 세션 확보 후 서비스 진입 | 저장/응답 실패에 대해 가입 여부 확인·로그인 재개 경로 제공 |
| 계정 관리 | 현재 계정, 연결된 로그인 수단, 복구 안내 | 로그인 수단 추가·해제·최근 본인확인·재시도 |
| 기록 가져오기 | 해당 기기에서 발견한 기존 기록 설명 | 가져오기/나중에, 대상 계정 확인, 중복·실패·중단 복구 |
| 로그아웃 | 현재 기기의 계정 접근 종료 설명 | 서버 폐기 실패 시 정확한 상태·재시도. 다른 계정 기록 노출 방지 |
| 회원탈퇴 | 삭제 대상·보존 예외·선택 내보내기 안내 | 최근 본인확인, 확인, 진행, 결과 미확인, 완료를 구분 |

‘미연결 소셜 ID’는 ‘다른 로그인 방식으로 가입된 회원이 전혀 없다’는 뜻이 아니다. 안내에서 이 차이를 지킨다.

## 6. 회원가입 구현 요구

1. 로그인/가입의 첫 진입을 통합한다. 사용자에게 가입 여부를 먼저 기억해 선택하도록 강요하지 않는다.
2. 모든 제공자는 인증 후 공통 회원 조회·분기·세션 확정 흐름을 사용한다. 공급자별 SDK 차이는 어댑터에 한정한다.
3. 최초 가입에서 이름·전화번호·교회 입력을 제거한다. 선택항목의 부재를 backend schema/DB/API가 정상 처리하는지 확인한다. 기존 회원 정보는 삭제하지 않는다.
4. 표시명은 필요한 경우 비민감 자동 별칭을 제공하고 나중에 수정할 수 있게 한다. 현재 기능에 불필요한 프로필 기능을 확대하지 않는다.
5. 만18세 이상이라는 현재 제품 정책을 유지한다. 자기 확인 체크를 실명/연령 본인인증 완료로 표시하지 않는다.
6. 약관/개인정보 안내 버전·동의시각·필수 여부를 일관되게 기록한다. 추가 동의의 필요성은 실제 처리 목적에 맞춰 판단한다.
7. 서버가 이미 가입된 ID를 반환하면 기존 로그인으로 회복한다. 동시 가입·중복 탭·재전송으로 회원을 여러 개 만들지 않는다.
8. 가입 서버 성공 후 로컬 회원번호/세션 저장 실패를 ‘가입 자체 실패’로 잘못 안내하지 않는다. 재시도 시 이미 생성된 회원으로 돌아올 수 있어야 한다.
9. 프로필과 서버 응답의 원문을 오류 메시지/로그에 표시하지 않는다.

## 7. 로그인·세션·네이버 A33 요구

1. 제공자 인증 성공, 자격증명 획득, 서버 신원 검증, 내부 회원 확인, 세션 발급, 안전한 로컬 저장, 계정 상태 확인을 구분한다.
2. 네이버 공식 SDK 콜백 계약과 실제 사용 버전을 대조한다. 버전 업그레이드는 근거·변경 범위·회귀검증 없이 일괄 적용하지 않는다.
3. 현재 후보의 `user_cancel`, `success_token_missing`, SDK 정리 실패 전달과 서버 신원 검증을 리뷰한다. 후보가 실제 release 산출물에 포함되는지도 확인한다.
4. 로그인 전 SDK logout 정책은 A33/S22의 실제 결과로 평가한다. 토큰 삭제·연동해제·앱 데이터 초기화를 임시 해결책으로 사용하지 않는다.
5. 네이버 앱 유무, Chrome 인증, 외부 인증 후 복귀, 뒤로가기, 앱 전환·재생성, 시간초과 후 늦은 콜백을 검증한다.
6. 동시에 여러 인증 요청을 열지 않는다. 이전 시도의 늦은 성공/401이 새 로그인·계정 선택을 덮어쓰지 못하게 한다.
7. 네트워크/5xx/저장장치 장애는 ‘확인 불가’다. 자동 미가입·자동 탈퇴·기존 계정 삭제로 처리하지 않는다.
8. 세션 만료와 실제 무효화는 서버 기준으로 확인한다. 기기 재시작·보안저장소 실패·만료 경계·시계차이·로그아웃 직후 저장 경합을 검증한다.
9. 진단은 허용된 고정 단계/코드만 사용한다. 토큰, 프로필, 전화번호, 종교·교회·대화, URL query, 전체 logcat을 수집하지 않는다.

## 8. 내부 회원번호와 기록 소유권

1. 기존 memberId와 provider identity mapping을 재사용한다. 새 계정 체계를 병렬로 만들어 회원이 갈라지게 하지 않는다.
2. 회원·소셜 ID·세션·기기 기록·서버 대화/사용량·초안·알림·동의·관리자 표시·삭제명부·백업의 실제 연결을 표로 작성한다. 현재 계정에 귀속되지 않는 항목을 명시한다.
3. 회원 전용 데이터는 검증된 내부 memberId로 접근을 제한한다. 클라이언트가 임의 memberId를 보내면 다른 회원에 접근할 수 없는지 API 권한 테스트를 한다.
4. 서버 account 응답을 사용할 경우 기존 계약을 보존하면서 필요한 내부 식별자 전달을 검토한다. UI에는 기술 식별자를 불필요하게 노출하지 않는다.
5. 로그아웃·계정전환 때 메모리 상태, 목록, 캐시, 진행 중 저장/로드 요청을 정리한다. A 계정의 늦은 응답이 B 계정 화면에 기록을 표시하지 못하게 한다.
6. 기존 기기 공용 기록은 소유자가 확인되지 않은 ‘이 기기의 이전 기록’으로 보존한다. 처음 로그인한 계정에 자동으로 귀속시키지 않는다.
7. 가져오기는 대상 계정과 기록 범위를 설명하고 사용자가 명시적으로 선택한다. 소유자를 입증하지 못한 공용 기록은 OS의 로컬 확인 등 필요한 보호를 검토하고, 입증된 다른 회원의 기록은 가져올 수 없게 한다.
8. 이관 전 비민감 명세/수량을 기록하고, 성공 검증 전 원본을 지우지 않는다. 반복 실행·부분쓰기·용량부족·앱 종료 후 복구·중복 ID·순서·손상 레코드를 검증한다.
9. 게스트/이전 기록과 회원 기록을 구분한다. 새로운 게스트 대화·클라우드 동기화 서비스를 이번 작업에 무조건 추가하지 않는다.
10. 회원가입 간소화보다 계정전환 시 다른 회원 기록이 보이는 문제 해결을 우선한다.

## 9. 소셜 연결·연결 해제·계정 복구

- 기존 회원 소유 증명과 새 제공자 인증을 모두 확인한 뒤 연결한다. 민감행위에 필요한 최신 본인확인 정책을 정의하고 검증한다.
- 이미 다른 회원에 속한 ID는 자동 이동/병합하지 않는다. 같은 이메일·이름·전화 입력만으로 동일인이라고 판단하지 않는다.
- 연결 중 새 소셜의 신규 가입을 실수로 실행하지 않도록 화면 목적을 명확히 표시한다.
- 마지막 유효 로그인 수단 해제를 막는다. 현재 로그인 수단 해제의 서버 규칙과 UI 안내를 일치시킨다.
- 실패/취소/중복 요청 시 기존 연결과 세션을 보존하고 부분완료를 회복한다.
- 복구 우선순위는 기존 로그인 방식 → 이미 연결된 다른 방식 → 실제 검증 가능한 복구수단 → 안전한 고객지원이다.
- 이메일 링크/휴대폰 인증은 기존 인프라·단일사용·만료·재사용 방지·요청 제한·계정 존재 노출 방지까지 확인한 경우만 구현한다. 새 유료서비스나 외부 계정 설정을 임의로 시작하지 않는다.
- 제공자를 사용할 수 없을 때 임의 새 계정 가입을 ‘복구’라고 안내하지 않는다. 현재 가능한 도움 경로를 제공한다.

## 10. 로그아웃·탈퇴·삭제의 끝까지 처리

### 로그아웃

- ONARIA 세션 종료, 기기 접근 종료, 공급자 로컬 상태 정리를 구분한다. 네이버/카카오 서비스 전체 로그아웃이나 외부 연동 해제를 의미한다고 안내하지 않는다.
- 실패를 완료로 숨기지 않는다. 오프라인에서 이 기기 접근을 먼저 잠글지 기존 상태를 유지할지 현재 구현을 검토해 명확한 정책을 정하고 서버 폐기 재시도까지 테스트한다.
- 세션/기록 접근을 메모리·영구저장소·재시작 관점에서 검사한다. 로컬 정리 실패를 알리고 다른 계정으로의 데이터 노출을 차단한다.

### 탈퇴

- ‘내 기록 내보내기’가 있으면 탈퇴 전 선택적으로 제시한다. 기능이 없으면 있는 것처럼 표시하지 않는다.
- 서버 회원정보, 연결 로그인 수단, 해당 회원 기기 기록/초안, 백업 보존예외와 처리 범위를 사용자 언어로 설명한다.
- 해당 계정의 최신 본인확인을 요구한다. Apple에 연결된 경우 기존 Apple 철회 증명 검증을 보존한다. 재인증된 소유자와 삭제 대상 memberId가 일치해야 한다.
- 서버 삭제·공급자 철회·전체 회원 세션 폐기·삭제명부·기기 삭제를 단계별로 설계한다. 공급자별 실제 철회 API 지원/계약을 확인한다.
- 부분실패·응답유실·앱 종료 후 결과조회/안전한 재시도를 제공한다. DB가 분리되어 있다고 원자적 전체삭제가 보장된다고 주장하지 않는다.
- 완료된 서버 삭제를 이후 기기 정리 실패로 서버 삭제 실패라고 오인시키지 않는다. 기기 잔여 정리 상태를 별도로 표시하고 재시도한다.
- 이 기기의 다른 회원 기록은 삭제하지 않는다. 회원소속 기록 삭제 방향을 채택하되 기존 실제 사용자 데이터는 승인 없는 파괴적 실험에 사용하지 않는다.
- 백업 복원으로 탈퇴 회원이 되살아나지 않는지 삭제명부까지 포함해 임시 DB로 검증한다. 정책·스토어 고지·보유기간·실제 자동파기를 일치시킨다.

## 11. 실행 순서와 각 단계의 완료 조건

| 순서 | 작업 | 다음 단계 진입 기준 |
|---|---|---|
| 0 | 현재 환경·변경·후보·테스트 확인 | 충돌 없이 수정할 범위와 기준 결과 기록 |
| 1 | A33 SDK 후보 리뷰·생애주기 재현 준비 | 취소/토큰누락/정리실패 분리 테스트, 서명된 후보. 사용자 인증이 필요하면 독립 작업 계속 |
| 2 | 회원번호·기기기록·세션 연결 조사/무손실 이관 | 소유권 표, 이관·롤백 계획, 격리 테스트 통과 |

## 13. 운영 경계와 기존 기능 보존

- 다른 프로젝트의 repo/branch/env/port/DB/deploy에 영향을 주지 않는다.
- `adb uninstall`, `pm clear`, 운영 DB 초기화, 서명키 교체, package 변경, 강제 다운그레이드 금지.
- 기존 release 서명 설정과 `com.onaria.app`을 유지한다. 실제 설정 충돌은 파일을 확인해 보고하며 추측해서 키를 교체하지 않는다.
- 후보 버전은 현재 모든 산출물/설치본/스토어 사용 번호를 확인한 후 단조 증가시킨다. Build21을 무조건 사용할 수 있다고 가정하지 않는다.
- 앱 정보 메뉴·API·진행로그에 후보 버전과 적용 범위를 추적한다. 배포 전 운영 API 버전을 바꾸지 않는다.
- 사용자 인증, 외부 계정 변경, 유료서비스, 운영 migration/배포/재시작, 실제 데이터 삭제는 현재 승인 범위를 확인한다. 승인 필요한 경우 후보·영향·검증·복구안을 먼저 준비한다.
- 안전응답, 위기입력의 외부 AI 호출 차단, 종교/성경 인용 무결성, 메뉴·스크롤·버전 표시·기존 기록을 회귀검증한다.
- 정책적 미확정사항을 코드로 임의 확정하지 않는다. 해당 단계만 보류하고 안전한 독립 작업은 완료한다.

## 14. 산출물·진행 기록·완료 판정

프로젝트 문서의 기존 체계를 재사용해 아래 내용을 유지한다. 파일을 불필요하게 여러 폴더에 복제하지 않는다.

1. 실제 회원 여정과 상태 전이, 화면별 문구·주요 행동·실패/복구 상태.
2. 내부 회원번호 기반 데이터 연결 표, 권한·이관·삭제·복원 설계.
3. 각 작업의 변경 파일·기준 SHA·후보 버전·검증 명령/종료값·미완료 항목.
4. 실제 화면에 근거한 UI 검증 결과. 구현하지 않은 기능의 스크린샷 금지.
5. 연속 작업 로그: 무엇을 했는지, 무엇이 실패했는지, 수정 내용, 다음 작업.
6. 최종 리뷰: 신규/기존/계정연결/기기전환/로그아웃/탈퇴의 전 과정, 기존 기록 보존, 다른 회원 비노출, 실기기 결과.

운영 health200, mock 성공, 컴파일 성공은 전체 회원 흐름 완료를 의미하지 않는다. A33 원인 미확정·계정경계·탈퇴/복원 등 핵심 미검증이 남으면 출시 HOLD를 유지한다. 승인을 기다린다고 모든 개발을 중단하지 않는다.

기존 변경이 섞인 파일은 전체 파일을 무조건 커밋하지 않는다. 이번 변경을 명확히 분리·검증할 수 있을 때만 저장소 규칙에 따라 commit/push하고 정확한 SHA의 CI를 확인한다. 원격과 운영 반영 여부를 각각 보고한다.

완료 보고에는 다음 YAML 항목을 사용하고, 실행하지 않은 항목은 이유와 함께 NOT RUN으로 표시한다.

```yaml
PROJECT:
CURRENT COMMIT:
ISSUE FOUND:
PRIORITY:
ROOT CAUSE:
IMPLEMENTED:
CHANGED FILES:
TEST:
BUILD:
DEVICE:
API:
CI:
COMMIT:
PUSH:
REMAINING RISKS:
NEXT ACTION:
```

## 15. Codex 시작 명령

이 작업지시서와 적용되는 AGENTS.md를 읽고 ONARIA의 현재 상태를 먼저 확인하라. 기존 작업과 데이터를 보존하면서 A33 인증 후보 검증, memberId 기반 기록경계, 가입/로그인 UX, 계정연결·복구, 로그아웃·탈퇴 순으로 실제 수정·검증을 진행하라. 단순 계획 제시로 멈추지 말고 안전한 로컬 작업은 계속하라. 사용자 인증이나 운영 변경이 필요한 단계는 준비된 후보와 정확한 미완료 사유로 남기고 독립적인 개발은 이어가라. 각 단계의 증거와 버전을 기록하고 미검증을 완료로 보고하지 마라.
